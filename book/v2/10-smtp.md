# SMTP(Simple Mail Transfer Protocol)

**SMTP**とは、インターネット上の通信のプロトコル(決まりごと)です。世の中のメールサーバ(postfix等)、メールクライアント(Outlook等)が全てSMTPに従うことで、メールのやり取りが可能になっています。みなさんがブラウザで利用するHTTPなどと同様に、クライアントが何らかの通信を行うと、サーバは、ステータスコードとメッセージを返却します。それらは、目には見えないテキストで構成されています。

メールサーバの運用上、**SMTP**で一番気を付けるべきポイントは、SMTPはステートフルであるということです。SMTP接続を行ったクライアント、および受け付けたサーバは、クライアントのリクエストに対してIPと入力された情報、特にメールの送信元メールアドレスや送信先メールアドレスに従った状態を持つということです。

**(1章で学ぶこと)**

- メールのデータには、メールアドレスや本文などの「見えるデータ」と、メールの送受信結果のような「見えないデータ」の2種類があること
- SMTPは、「あなたは誰か」や「本文の内容」などを順番に伝え、複数回行き来する通信であること

\clearpage

## 見えるデータ

皆さんは、メールを利用していますでしょうか。この本を手に取っている皆さんは、技術書典にメールアドレスを使って登録・ログインをする際にメールの送受信を行なっているはずです。

例えば、メールソフトであるThunderbirdを見ると、以下のような見慣れた画面が表示されることでしょう。ここには、「送信元メールアドレス」、「宛先メールアドレス」、「本文」と、いくらかの添付ファイルが表示されることが多いかと思います。これらは、メーラーなどを使って「見えるデータ」であり、RFC 5322[^10-rfc5322]という文書でファイルの中身をどのように記述すればいいかが定義されています。

## 見えないデータ

ここで、「その他」から「ソースを表示」ボタンをクリックすると、以下のような画面が表示されます。これは、実際に、GmailやOutlookといったメールサーバに保存されるデータの中身です。

![メールソフト「Thunderbird」上の「ソースを表示」画面](10-04-メールソフト「Thunderbird」上のソースを表示画面){ width=100% }

「見えるデータ」には書いてない、Return-PathやReceivedといった普通は「見えないデータ」が存在することがわかりますね。メールの運用者は、この「見えるデータ」と「見えないデータ」を調整したり、トラブルシューティングしたりしていくことになります。

\clearpage

## エンベロープFrom(Return-Path)とヘッダーFrom(RFC5322.From)

ここで、一番最初に大事なことを整理します。「見えるデータ上の送信元メールアドレス」と「見えないデータ上の送信元メールアドレス」の区別です。これは、メール運用者が必ずつまづく点でもあります。

実際に例を見てみましょう。以下の画像の中では、上の方では `Return-Path: <user1@a.test>` となっていますが、下の方では `From: user2@a.test` となっていることがわかります。そして、メーラー上は「`user2@a.test`」が送信元となっていますね。これは、`From` が見えるデータのFrom、いわゆるヘッダーFromと言われ、`Return-Path` というのが、見えないデータのFrom、いわゆるエンベロープFromと言われます。

![Return-PathとFromが異なる例](10-05-Return-PathとFrom.png)

\clearpage

なぜ2つあるのか。これは、ユーザから見た場合はヘッダーFromが表示され、メールサーバはエンベロープFromを元に制御を行う、という大きな違いがあります。特にエンベロープFromは、Return-Pathという名の通り、メールが何らかの理由でエラーとなった場合はこのメールアドレスにエラーの通知が行われます。MAILER-DAEMONなどから来るメールはこちらを元にメールを送信している、と言うわけですね。

通常、ThunderbirdやOutlook等のソフトウェアを使っている場合、この2つのFromは必ず一致しています。しかし、何らかのシステムからメールを送ったり、あるいは悪用しようとする人はエラーメールが邪魔なので知らない人のメールアドレスをエンベロープFromに設定してなりすましたりとすることがあります。

\clearpage


## SMTPの通信内容

しかし、何故このような2つのFromができてしまうのでしょうか。SMTPの通信を詳しく見てみましょう。

右図の例中に灰色で示した 220 や 250 、354といったステータスコードから始まる行がサーバのレスポンスです。これらは、「あなたは誰ですか」「メールの宛先は誰ですか」「本文をどうぞ」「受け付けました」といった順序に合わせたレスポンスです。皆さんが実際に書くメールの宛先、タイトル、本文以外にもいろいろと通信が行われていることがわかります。

このような通信を世界中で統一した規格がSMTPであり、WindowsやMac、iPhoneやAndroid、OutlookやGmailといった、完全に違うハードウェアやOS、ソフトウェア同士でも、全てがこの決まりを守ることから、メールをやりとりできる世界が作られています。

今の解説中にこの途中で重要な概念が出てきました。「あなたは誰ですか」と「本文をどうぞ」で別々のやり取りを行なっているという点です。つまり、「あなたは誰ですか」はエンベロープFromであり、「本文をどうぞ」がヘッダーFrom部分です。

SMTPはとても古く、1982年のRFC 733[^10-rfc733]には、Return-Pathを書く決まりが定まりました。この仕様を受け継いでいることから、エンベロープFromとヘッダーFromが別々にあり、世のメール管理者の混乱を招いている一因でもあります。

メールの具体的なイメージが湧きたところでしょうか。それでは、さらにメールの送受信を支える、世の中のさまざまな仕組みについて触れていきましょう。

[^10-rfc733]: https://datatracker.ietf.org/doc/html/rfc822

\clearpage
